## 3. Distance-Vector Routing (9 points)

拓扑边权：

```text
A-B = 21
A-D = 15
B-C = 18
B-D = 12
C-D = 5
C-E = 11
D-E = 17
```

Distance-vector 的更新公式是：

$$
D_E(X) = \min_{v \in N(E)} \{ c(E,v) + D_v(X) \}
$$

其中 $N(E)=\{C,D\}$，因为 Eve 只直接连到 C 和 D。

### 3(a) Show the initial routing table of node E

初始状态下，E 只知道自己直接相邻的节点 C 和 D；到 A、B 没有直接边，所以是 $\infty$。

| Destination | Cost | Next Hop |
| ----------- | ---: | -------- |
| A | $\infty$ | --- |
| B | $\infty$ | --- |
| C | 11 | C |
| D | 17 | D |

### 3(b) Show the routing table of node E after one iteration

第一轮只使用邻居 C、D 的初始 distance-vector。

- 到 A：
  - 经 C：$11+\infty=\infty$
  - 经 D：$17+15=32$
  - 所以选 D，cost = 32。
- 到 B：
  - 经 C：$11+18=29$
  - 经 D：$17+12=29$
  - 两条一样，所以 `C or D` 都可以。
- 到 C：直接边是 11，仍然最优。
- 到 D：
  - 直接边：17
  - 经 C：$11+5=16$
  - 所以改成经 C，cost = 16。

| Destination | Cost | Next Hop |
| ----------- | ---: | -------- |
| A | 32 | D |
| B | 29 | C or D |
| C | 11 | C |
| D | 16 | C |

### 3(c) Show the routing table of node E after two iterations

第二轮邻居的表也已经更新过，所以 E 能学到更短路径。

- 到 A：最短是 $E \to C \to D \to A$，cost $=11+5+15=31$，next hop 是 C。
- 到 B：最短是 $E \to C \to D \to B$，cost $=11+5+12=28$，next hop 是 C。
- 到 C：直接到 C，cost = 11。
- 到 D：经 C 更短，$11+5=16$。

| Destination | Cost | Next Hop |
| ----------- | ---: | -------- |
| A | 31 | C |
| B | 28 | C |
| C | 11 | C |
| D | 16 | C |

### 3(d) Failure convergence

#### 3(d)(1) What problem with the distance vector protocol is the cause?

答案：**count-to-infinity problem**。

解释：distance-vector 节点只知道“邻居声称到某目的地的距离”，不知道完整路径。链路失效后，两个节点可能互相误以为对方还有通路，于是距离一点点增加：

```text
A thinks B can reach X
B thinks A can reach X
cost keeps increasing: 3, 4, 5, ..., infinity
```

这就是收敛很慢的原因。

#### 3(d)(2) Why does BGP not suffer from this problem?

答案：BGP 是 **path-vector protocol**。

BGP advertisement 不只是说“我到目的地 cost 多小”，还携带 AS path，例如：

```text
AS7 AS3 AS2 AS1
```

如果一个 AS 收到的路径里已经包含自己，就知道这条路会形成 loop，直接拒绝。因此 BGP 可以用路径信息避免典型 distance-vector 的 count-to-infinity。

## 4. Routing, addressing, and tunneling (9 points)

这题核心是区分三层东西：

```text
Ethernet header: 每一跳都会变，因为它只负责当前链路上的 next hop。
IP header: 端到端的内层 IP 通常不变；NAT 会改源 IP。
Tunnel header: 外层 IP / MPLS 是为了穿过 tunnel 临时加的。
```

H1 发往 H2。H1 私有地址是 `10.0.0.2`，经过 NAT 后对外源地址变成 `1.2.3.4`。H2 地址是 `3.0.1.2`。

### 4(a) Header for packet 2

packet 2 是 H1 在左侧 LAN 里发给 NAT inside interface。

| Header Type | Source | Destination |
| ----------- | ------ | ----------- |
| Ethernet | MAC 1 | MAC 2 |
| IP | 10.0.0.2 | 3.0.1.2 |

解释：

- 二层目的 MAC 是 NAT inside 的 MAC，因为 H1 要把包先交给默认网关。
- 三层目的 IP 仍然是 H2，不是 NAT；IP 层表达的是最终目的地。

### 4(b) Header for packet 3

packet 3 是 NAT 出口发出的包。

| Header Type | Source | Destination |
| ----------- | ------ | ----------- |
| Ethernet | MAC 3 | MAC 4 |
| IP | 1.2.3.4 | 3.0.1.2 |

解释：

- NAT 把源 IP 从 `10.0.0.2` 改成自己的公网地址 `1.2.3.4`。
- Ethernet MAC 仍然只是当前链路上的下一跳：MAC 3 到 MAC 4。

### 4(c) Header for packet 4

packet 4 在 tunnel 中间，同时有 MPLS 和 IP tunnel。

| Header Type | Source | Destination |
| ----------- | ------ | ----------- |
| Ethernet | MAC 9 | MAC 10 |
| MPLS | X | X |
| IP | 1.2.3.6 | 2.0.0.1 |
| IP | 1.2.3.4 | 3.0.1.2 |

解释：

- MPLS header 没有 source/destination address，所以填 `X`。
- 外层 IP 是 tunnel endpoint：`1.2.3.6 -> 2.0.0.1`。
- 内层 IP 才是被封装的原 packet：`1.2.3.4 -> 3.0.1.2`。

### 4(d) Header for packet 5

packet 5 已经离开 MPLS 部分，但 IP tunnel 还在。

| Header Type | Source | Destination |
| ----------- | ------ | ----------- |
| Ethernet | MAC 11 | MAC 12 |
| IP | 1.2.3.6 | 2.0.0.1 |
| IP | 1.2.3.4 | 3.0.1.2 |

解释：

- MPLS header 被剥掉了，所以不再出现 MPLS 行。
- 外层 IP tunnel header 还没被 decapsulate，所以仍有两层 IP header。

## 1. Transporting a file (15 POINTS)

文件大小：250,000 bytes。链路速率：2,000,000 bits/s。

### 1(a)

计算：

$$
250000\ \text{bytes} \times 8 = 2000000\ \text{bits}
$$

链路速率是 $2,000,000$ bits/s，所以：

$$
\frac{2000000}{2000000}=1\ \text{second}
$$

答案：**1 second**。

### 1(b)

MSS = 1000 bytes，文件大小是 250,000 bytes，所以总共约 250 MSS。

TCP 开始前需要 1 RTT 做 handshake。然后 slow start 每 RTT 发送窗口翻倍：

```text
1, 2, 4, 8, 16, 32, 64, 128 MSS
```

总和：

$$
1+2+4+8+16+32+64+128 = 255\ \text{MSS}
$$

255 MSS = 255,000 bytes，已经超过文件大小。因此数据传输需要 8 RTT，再加 handshake 1 RTT。

答案：**9 RTT**。

注：若不要求最后一批数据被 ACK，某些计数法会得到 7.5 RTT 的传输部分；考试答案接受这种边界解释。

### 1(c)

题目说“single packet is lost”，并且意图是 **triple duplicate ACK** 检测到丢包。

TCP Reno 的反应：

```text
cwnd / rate 减半，然后 additive increase
```

当前速率：32,000 bytes/s。减半后：

$$
32000/2=16000\ \text{bytes/s}
$$

之后每 RTT 增加 1 MSS = 1000 bytes/s，因此从 16,000 回到 32,000 需要：

$$
\frac{32000-16000}{1000}=16\ \text{RTTs}
$$

答案：**下一速率 16,000 bytes/s；恢复需要 16 RTTs**。

### 1(d)

如果所有 packet 都丢了，就不会有足够 duplicate ACK，只能靠 **timeout** 检测。

timeout 后：

```text
cwnd = 1 MSS
ssthresh = old cwnd / 2 = 16 MSS
先 slow start 到 16 MSS
再 additive increase 到 32 MSS
```

若按隐含 RTT = 1s，速率单位等价于 MSS/RTT：

- 从 1 MSS slow start 到 16 MSS：$1,2,4,8,16$，约 4 RTT。
- 从 16 MSS additive increase 到 32 MSS：16 RTT。

答案：**下一速率 1000 bytes/s；恢复约 20 RTTs**。

## 2. Sockets (16 POINTS)

### 2(a) TCP socket call ordering

判断原则：

```text
Server: socket -> bind -> listen -> accept -> recv
Client: socket -> connect -> send -> close
```

其中：

- `connect()` 需要服务器已经 `listen()`，并最终由 `accept()` 接受。
- `accept()` 没有客户端连接时会阻塞。
- `recv()` 要在有连接、有数据后才可能收到数据。

#### Scenario i

答案：**No**。

原因：client 在 server `listen()` 之前就 `connect()`，连接不能正常建立；没有有效连接，后面的 `send()` 不可能被 server `recv()` 到。

#### Scenario ii

答案：**No**。

原因：client `connect()` 时 server 还没有 `socket/bind/listen`，所以连接建立不了。

#### Scenario iii

答案：**Yes**。

原因：server 已经 `socket -> bind -> listen -> accept` 等待，client 再 `connect -> send`，顺序合理。

#### Scenario iv

答案：**No**。

原因：server 的 `accept()` 在 client `connect()` 前会阻塞；如果按题目顺序要求本地下一步必须等当前调用返回，那么 server 到不了 `recv()`。

#### Scenario v

答案：**Yes**。

原因：即使 client 先调用 `connect()`，只要 server 随后 `bind/listen/accept` 能完成连接建立，之后 `send()` 再发生，server 可以 `recv()` 到。

### 2(b) TCP stream socket: ten sends

#### i) Can TCP transmit more than ten packets?

答案：**Yes**。

原因：TCP 是 byte stream，不保持应用层 `send()` 边界。如果一次 `send()` 的数据大于 MSS，就会被拆成多个 TCP segment，所以十次 `send()` 可能产生超过十个 data packet。

#### ii) Can TCP transmit fewer than ten packets?

答案：**Yes**。

原因：小的 `send()` 可以被 TCP 合并到同一个 segment 中，例如 Nagle algorithm 会合并小写入，减少 tiny packets。

### 2(c) UDP datagram socket: ten sendto

#### i) Can UDP transmit more than ten packets?

答案：**Yes**。

原因：UDP 保留 datagram 边界，但如果某个 UDP datagram 超过 MTU，IP 层可能 fragmentation，于是一个 UDP datagram 对应多个 IP fragments。

#### ii) Can UDP transmit fewer than ten packets?

答案：**No**。

原因：UDP 不像 TCP 那样把多个 `sendto()` 合并成一个 datagram。一次 `sendto()` 对应一个 UDP datagram；除非丢包，否则不会少于十个 datagram。

## 3. Your Web Browser in action (17 POINTS)

### 3(a) Packet ordering

答案顺序：

```text
11, 7, 2, 3, 12, 9, 4, 5, 10, 8
```

解释：

1. `11`：A 刚启动，先 DHCP 获取网络配置。
2. `7`：A 要访问 cache C，需要把 IP 包交给网关或本地下一跳，因此先 ARP。
3. `2`：A 向 Web cache C 发出 HTTP proxy-style request：`GET http://S/index.html`。
4. `3`：C 的 local nameserver NL 去 root 查询 S。
5. `12`：NL 再向 authoritative nameserver NA 查询 S。
6. `9`：NL 把 S 的地址返回给 C。
7. `4`：C 与 S 建 TCP 连接，发送 SYN。
8. `5`：C 向 S 请求 `index.html`。
9. `10`：S 把 `index.html` 返回给 C。
10. `8`：C 把内容返回给 A。

### 3(b) Subsequent request eliminated messages

答案：

```text
11, 7, 3, 12, 9, 4, 5, 10
```

解释：

- `11` DHCP：网络配置已缓存/租约有效，不用重新 DHCP。
- `7` ARP：ARP cache 已有。
- `3,12,9` DNS：如果 C 已经缓存了 object，就根本不需要解析 S。
- `4` TCP SYN：persistent connection 已经存在，不用重新连接。
- `5,10` C 不需要向 S 请求，因为 Web object 已在 C 的 cache 中。
- 仍然需要 `2` 和 `8`：A 仍向 C 发请求，C 仍返回对象。

## 4. A routed and bridged network (14 POINTS)

核心原则：

```text
Bridge/switch 看二层 MAC。
Router 改二层 next-hop MAC，但不改三层源/目的 IP。
Host 发往异网段时，二层目的 MAC 是默认网关的 MAC。
```

### 4(b)

答案：`R2a.mac`。

解释：H1 要发给远端 H2，不在同一 LAN，所以帧的二层目的地是默认网关 R2 的入口接口 MAC。

### 4(c)

答案：`R2c.mac`。

解释：包离开 R2 后，新的 Ethernet frame 由 R2c 接口发出，所以二层源 MAC 是 `R2c.mac`。

### 4(d)

答案：`H1.ip`。

解释：Router 转发 IP packet 时不改三层源 IP；除非 NAT，但这里只是普通 router。

### 4(e)

答案：`R2a.mac has R2a.ip`。

解释：H1 ARP 的目标是默认网关接口 R2a 的 IP，收到的 reply 是 R2a 的 MAC。

## 5. Multiple choice (16 points)

### 5(f) DNS

正确：**A, C**。

- A 正确：一个 A record 查询可以返回多个 IP，例如负载均衡或多副本服务。
- B 不按标准表述：NS record 返回的是 nameserver name，不是直接多个 IP 地址；IP 可能通过 additional section 或额外 A 查询得到。
- C 正确：NS record TTL 太短会导致 resolver 更频繁回到 root/GTLD 查 delegation，增加高层 DNS 压力。
- D 错：A record TTL 短主要增加 authoritative server 压力，不一定增加 root/GTLD 压力，因为 delegation NS 仍可能缓存。

### 5(g) Web caches

正确：**A, B**。

- A 正确：web cache/proxy 可以代替 origin server 满足客户端 HTTP 请求。
- B 正确：对 client 来说 cache 是 server；对 origin server 来说 cache 是 client。
- C 错：HTTP 明确支持 caching 和 cache consistency，如 `Cache-Control`, `Expires`, `ETag`, `If-Modified-Since`。
- D 错：不是所有 HTTP object 都可缓存，动态内容、带认证内容、明确 `no-store` 的内容都可能不可缓存。

### 5(h) Persistent HTTP connections

严格正确：**B**。

- B 正确：如果页面对象都来自同一 server，persistent HTTP 可以只开一个 TCP connection 下载多个 object。
- A 严格说错：persistent connection 不是 application-level session；session 通常靠 cookie。
- C 错：persistent connection 对许多小对象收益最大，而不是大对象。
- D 错：persistent 的特点就是 server 不一定马上关闭连接。

## 6. Short Answer (22 points)

### 6(a) Soft state

Soft state 是临时状态，不要求永久一致或显式删除；通常靠 timeout / lease / refresh 维持。

例子：

```text
ARP cache
DNS cache
DHCP lease
NAT binding
```

优点是故障后可以自然过期，不需要复杂恢复；缺点是需要刷新，可能浪费流量或状态空间。

### 6(b) Exponential backoff

两个典型例子：

1. **TCP congestion control**：丢包后 multiplicative decrease。若不 backoff，路由器队列持续满，丢包更严重，甚至 congestion collapse。
2. **Ethernet CSMA/CD**：碰撞后随机指数退避。若不退避，节点会不断同时重传，继续碰撞。

### 6(c) Why retransmit SYN?

可能原因：

```text
SYN 在路径上丢了
SYN 被校验和错误丢弃
B 的 listen backlog 满了
SYN-ACK 在返回路径丢了
A 的 RTO 太短，过早 timeout
SYN 被 firewall/NAT 丢弃
```

### 6(d) Why DNS over UDP?

DNS 查询通常是小型 query/response。用 UDP 可以避免 TCP connection setup 的额外 RTT 和连接状态开销。UDP 也更适合 anycast DNS，因为没有长连接状态要维护。

### 6(e) Why NAT?

常见原因：

- 缓解 IPv4 地址不足：多个 private hosts 共享一个 public IP。
- 隐藏内部网络结构：外部只看到 NAT 地址。
- 内部重编号方便：内部私网地址变化不影响外部地址。
- 有一定防火墙效果：默认阻止外部主动连接内部主机。

### 6(f) NAT changes what fields?

出 LAN 到 Internet 时，NAT 通常改：

```text
source IP address
source port
IP header checksum
TCP/UDP checksum
```

因为 IP/port 改了，checksum 也必须重算。

### 6(g) ECN

传统拥塞检测靠 **packet loss**：路由器队列满后丢包，sender 把丢包当作拥塞信号。

ECN 是显式标记：路由器不丢包，而是在 IP header 中打标记告诉端系统“已经拥塞”。

优点：避免不必要丢包和重传，尤其对交互式流量更好。缺点：需要 sender、receiver、router 都支持，部署困难。

### 6(h) OSI layers examples

常见对应：

| Layer | Example |
| ----- | ------- |
| Application | HTTP, DNS, SMTP |
| Presentation | TLS/SSL, encoding/compression |
| Session | RPC/session management，课程里通常弱化 |
| Transport | TCP, UDP |
| Network | IP, ICMP |
| Link | Ethernet, WiFi, ARP 相关链路机制 |
| Physical | copper, fiber, radio |

# Spring 2008 Mid

## 1. Big MAC (15 points)

### 1(a)

今天的 Internet 用 IP 地址表达 topology location。主机移动到另一个网络后，IP 地址通常会变；TCP/UDP socket 绑定了原来的地址/端口，所以持续连接很难保持。

如果全 Internet 用全球唯一 MAC 作为 endpoint identifier，那么主机移动后 identifier 不变，理论上 mobility 更容易：DNS 返回同一个 MAC，不需要因为位置变化改变 endpoint name。

### 1(b)

在没有 IP 地址的世界里：

- DHCP：不再需要分配 IP/netmask，但可能仍需要配置 DNS server、gateway 等信息。
- ARP：不再需要，因为 ARP 的作用是 IP -> MAC mapping。
- MAC learning：仍然需要，switch/bridge 仍要学习某个 MAC 在哪个端口后面。

### 1(c)

转发表会变得巨大。

原因：MAC 地址是 flat address，不含层级拓扑信息，不能像 IP prefix 一样聚合。例如 IP 可以用一个 prefix 表示一个机构/ISP 的大量主机；MAC 需要接近逐主机记录。LAN 内 switch 表大小可能差不多，但 Internet-wide forwarding table 会爆炸。

## 3. Going With the Flow (10 points)

### 3(a)

带宽升级后网页访问没明显改善，可能因为瓶颈不在 access link，而在：

- RTT / latency：短 Web transfer 往往被 DNS、TCP handshake、HTTP request RTT 主导。
- TCP receive window：吞吐上限约为 $\text{RWIN}/\text{RTT}$。
- server 端慢或网页对象很多。
- short flows 没跑出 slow start。

### 3(b)

goodput 下降的原因是拥塞时大量 packet 已经消耗了前面链路资源，最后却在后面被丢弃。丢弃后 sender 还要 retransmit，进一步浪费带宽。于是链路忙于传输“最终不会成功交付的数据”，成功交付率反而下降。

### 3(c)

无线丢包常常是 bursty loss：干扰/遮挡可能让一整个窗口内多个包都丢。triple duplicate ACK 需要“后面的包成功到达”才能触发 duplicate ACK；如果后面的包也丢了，就只能 timeout。

性能影响：timeout 比 triple duplicate ACK 慢得多，而且会把 cwnd 降到更低，吞吐下降更严重。

### 3(d)

大 buffer 的好处：吸收 burst，短时间突发不会立刻丢包。

大 buffer 的坏处：

1. 增加 queueing delay，造成 bufferbloat。
2. TCP 更晚感知拥塞，因为包可以在队列里排很久。
3. 成本更高，内存/功耗更大。

## 4. Caught in the Web (15 points)

### 4(a)

TCP 三次握手：

```text
A -> B: SYN
B -> A: SYN-ACK
A -> B: ACK
```

- A 最早在收到 SYN-ACK 后可以发 data，因为此时 A 知道 B 收到了自己的 ISN。
- B 最早在收到 A 的 ACK 后可以认为连接完全建立并发 data，因为此时 B 知道 A 收到了 B 的 ISN。

### 4(b)

HTTP pipelining 中多个 request 在同一个 TCP byte stream 中连续发送。server 不能靠 TCP packet 边界识别 request，因为 TCP 只提供字节流。server 必须 parse HTTP syntax，例如：

```text
CRLF line endings
Content-Length
chunked encoding
```

### 4(c)

`read()` / `recv()` 不保证返回一个完整 HTTP request，原因：

1. TCP 是 byte stream，不保留应用层 message boundary。
2. request 可能比分配的 buffer 大。
3. request 的后半部分可能还没到达，`recv()` 先返回已到达的字节。

### 4(d)

persistent connection / pipelining 的目的：

- 减少频繁建立/关闭 TCP 连接的开销。
- 避免每个对象都重新 slow start。
- 减少 RTT 等待。
- 对同一路径上的多个客户端更公平。

浏览器常禁用 pipelining 的原因：

- parallel connections 可能给自己抢到更多带宽。
- 多个图片可以并行显示，用户感知更快。
- pipelining 还会遇到 head-of-line blocking 和服务器兼容性问题。

## 5. Losing Control (15 points)

### 5(a)

FTP active mode 中，client 在 control connection 里告诉 server：请连接我的某个 IP:port 来建立 data connection。

NAT 后有两个问题：

1. client 发出的 PORT command 里可能是 private IP，server 不能从公网路由到它。
2. server 主动向 client 建连接时，NAT 还没有现成 mapping，会把 SYN 丢掉。

### 5(b)

NAT 若要支持 active FTP，需要做 application-layer gateway：

```text
parse FTP control connection on port 21
extract PORT command
rewrite private IP/port to public IP/port
create NAT table entry for upcoming data connection
update checksums
```

### 5(c)

重写 PORT command 可能改变 payload 长度，因为十进制 IP/port 字符串位数可能不同。TCP sequence number / ACK number 是按字节编号的，所以 NAT 还要调整后续 TCP seq/ack；如果 packet 变大超过 MTU，还可能 fragmentation。

### 5(d)

如果其他应用也用 port 21，NAT 可能误以为它是 FTP，错误 parse/modify payload。如果 FTP control connection 加密，NAT 看不到 PORT command，就无法做正确重写。这说明 NAT 破坏了 layering：网络设备不得不理解应用层协议。

### 5(e)

Passive mode 中 server 选 port 并告诉 client，client 主动连接 server 的 data port。对 client-side NAT 更友好，因为连接仍是内部 client 主动发起，NAT 可以自然创建 mapping。

## 1. Weighting it Out (10 points)

### 1(a)

若目标是最少 hop，把所有 link weight 设为同一个值，例如 1。这样 shortest path 就等价于最少边数路径。

### 1(b)

## 10. Concurrency, races, and synchronization

判断标准：是否所有 thread 都可能读到同一个会变化的 `i` 地址，从而打印错误 ID。

### 10(a)

答案：**No race**。

每次循环都 `Malloc(sizeof(int))`，把当前 `i` 拷贝到独立 heap object，再把 pointer 传给 thread。每个线程读的是不同内存，读完还 `Free`，不会被 main loop 的 `i` 修改影响。

### 10(b)

答案：**Yes race**。

所有 thread 都收到 `&i`，也就是 main thread 的同一个 loop variable 地址。线程真正执行 `myid = *((int *)vargp)` 时，main 可能已经把 `i` 改成下一个值，甚至循环结束，所以可能打印重复或错误 ID。

### 10(c)

答案：**No race**。

这里把 `i` 的值本身 cast 成 `void *` 传入，而不是传 `&i` 的地址。thread 中再 cast 回 int，读到的是创建时的值副本，不依赖 main 的变量地址。

注：现代 C 中整数和指针直接 cast 有可移植性问题，但这道题考的是 race。

### 10(d)

答案：**Yes race**。

虽然 thread 中用 semaphore 包住了读取 `*vargp`，但 main thread 修改 `i` 没有被同一个 semaphore 保护。锁只在线程之间互斥，不能阻止 main 在线程读取前继续改变 `i`。

### 10(e)

答案：**No race**。

main 每创建一个 thread 后立即 `P(&s)` 等待；thread 读取 `*vargp` 后 `V(&s)` 通知 main 可以继续下一轮。因此 main 不会在该 thread 读取 `i` 前修改 `i`。

```text
Client: socket -> connect
```

client 一般不需要 `bind`，内核会自动分配 ephemeral port。server 需要 `bind` 到 well-known port，然后 `listen/accept`。

### 6(b) Webcam recv bug

bug：`recv(server_fd, image_buf, 4096, 0)` 不保证一次读满 4096 bytes。

即使 server 确实发送了 4096 bytes，client 这次 `recv` 可能只返回 1000、2000 等部分数据。代码只检查 `<0`，没有检查正返回值是否等于 `IMAGE_SIZE`。

正确逻辑：循环 `recv`，累计已读字节，直到读满 4096、遇到 EOF 或出错。

## Spring 2009 Final

### 6(a) Error Handling

并发 echo server 的三个错误处理：

```text
socket error: exit(-1)
recv error: break
send error: break
```

解释：

- `socket()` 初始化失败，server 无法继续，直接退出。
- `recv()` 在某个 connection 上失败，只结束该 connection 的处理循环。
- `send()` 失败同理，断开/结束该 connection，不能影响整个 server。

### 6(b) Network Bugs

#### Bug 1: global buffer race

`buffer` 是全局变量，被多个 connection-handling threads 共享。线程 A 正在读/写 buffer 时，线程 B 可能覆盖同一块 buffer，导致 echo 内容串线或损坏。

修复：把 buffer 改成 `handleConnection()` 的局部变量，保证每个 thread 有自己的 buffer。

#### Bug 2: send short count

`send()` 不保证一次发完所有 bytes。即使返回正数，也可能小于要发送的长度。

错误代码如果忽略正返回值，就会只发出 buffer 的前一部分。

修复：写 `sendall` 循环：

```c
int sent = 0;
while (sent < len) {
    int n = send(fd, buf + sent, len - sent, 0);
    if (n <= 0) break;  // handle error/closed connection
    sent += n;
}
```
